# SelloQ — MVP Build Plan

> Marketing & sales intelligence platform. A company admin adds their website and documents. SelloQ builds a **Company Profile**, derives an **Ideal Customer Profile (ICP)**, generates **Signals** (buying triggers to watch for), runs them across the internet through **MCP servers**, and shows the resulting **Leads** in a feed. The user can then act on each lead by email, call or WhatsApp.

---

## 0. TL;DR

| Item | Decision |
|---|---|
| Backend | **FastAPI** (Python 3.12). Express isn't needed: FastMCP, the OCR/parsing libraries and the LLM tooling are all Python, so one language covers everything. |
| Background jobs | **arq** (async Redis queue). It's lightweight and runs async code natively, which fits the FastMCP client. |
| MCP servers | **FastMCP 2.x** (`fastmcp>=2.12,<3`) for the custom servers. Locally they run in Docker over streamable HTTP; in production they run on **FastMCP Cloud**. |
| MCP client | **FastMCP `Client`**, not LangChain MCP adapters (see §4.3 for why). |
| LLM | OpenAI (`OPENAI_API_KEY`), Structured Outputs into Pydantic models. Model names are configurable through env. |
| DB | **PostgreSQL 16** (JSONB for AI documents; `pgvector` added later). SQLAlchemy 2 (async) + Alembic. |
| Cache/queue | **Redis 7**: arq queue, hit dedupe, rate limiting. |
| Frontend | **React + Vite + TypeScript**, TanStack Query, React Router, Tailwind + shadcn/ui. |
| Local run | `docker compose up --build` starts the stack **`test-selloq`** (Postgres, Redis, backend, worker, frontend, MCP servers, demo sites, Mailpit). |
| Demo | Two fully seeded end-to-end flows: **NordWave Networks** and **LedgerLeaf**. Each has a profile, ICP, signals and leads found via MCP calls. |

## 1. MVP Scope

### In scope
1. **Auth & workspace**: register/login (email + password, JWT). Each user owns one or more *workspaces* (one per seller company, e.g. "Nokia").
2. **Company Profile**: website URL plus uploads (PDF, DOCX, XLSX/CSV, PNG/JPG, MP4/MP3). MCP servers crawl and parse them, then the LLM writes a structured profile the user can edit.
3. **ICP**: generated by the LLM from the profile. The user can edit and regenerate it, and ICP versions are kept.
4. **Signals**: generated by the LLM from the ICP. Each signal has a type, a source, query templates and a weight. The user can toggle and edit signals.
5. **Lead discovery**: the signal runner calls MCP search tools, the LLM extracts and qualifies prospects, and leads are deduped, scored and stored together with the evidence that triggered them.
6. **Signal Feed**: a list of leads with the matching signal, evidence link, snippet and score. Actions: **Email** (AI draft, sent via SMTP, captured by Mailpit locally), **Call** (`tel:` link plus outcome log), **WhatsApp** (`wa.me` deep link with an AI-drafted message), and status changes. Every action is logged as an Activity.
7. **Two seeded demo flows** that work right after `docker compose up`.

### Out of scope (MVP)
Billing, teams/RBAC beyond owner, CRM sync, real outbound sequencing, LinkedIn automation, a real WhatsApp Business API, and multi-language support.

```
                         │ worker (arq)             │────────────────┘
                         │  pipelines: profile, icp,│

                         │  MCP Hub (FastMCP Client)│
                         └──┬──────────┬─────────┬──┘
           streamable HTTP  │          │         │  (remote, optional)
        ┌───────────────────▼┐ ┌───────▼──────┐ ┌▼──────────────────────────┐
        │ mcp-webscraper     │ │ mcp-docparser│ │ mcp-signals               │
        │ crawl/scrape :9001 │ │ OCR/PDF/XLSX │ │ web/news/social/jobs      │
        └─────────┬──────────┘ │ video :9002  │ │ search + enrich  :9003    │
                  │            └──────────────┘ │ PROVIDER_MODE=fixture|live│
        ┌─────────▼──────────┐                  └───────────────────────────┘
        │ demo-sites (nginx) │        + optional third-party remote MCPs
        │ fictional company  │          (Tavily / Exa / Firecrawl / Brave …)
        │ websites :8080     │        mailpit :8025 (captures outbound email)
        └────────────────────┘
```

**Key principle:** pipelines never call a scraping or search API directly. They ask the **MCP Hub** for a *capability* (`scrape`, `doc_parse`, `web_search`, `news_search`, `social_search`, `job_search`, `enrich`), and the hub routes the request to whichever configured MCP server provides it. Swapping the demo fixtures for live providers, or adding a new MCP, is then a config change only.

## 4. MCP Layer

### 4.1 Custom MCP servers (FastMCP 2.x)

All three are FastMCP servers using the `http` (streamable HTTP) transport, protected by a bearer token (`MCP_SHARED_TOKEN`). The same code runs in Docker and on FastMCP Cloud.

**`mcp-webscraper`** (capability: `scrape`)
| Tool | Input | Output |
|---|---|---|
| `scrape_url` | `url` | `{url, title, markdown, links[]}` |
| `crawl_site` | `url, max_pages=15, same_domain=True, include_paths?[]` | `[{url, title, markdown}]` |

Built with `httpx` + `trafilatura` (HTML → markdown) and a breadth-first crawl that prioritises `/about`, `/products`, `/solutions`, `/customers`, `/industries` and `/pricing`. Playwright for JS-heavy sites is a later improvement. If `FIRECRAWL_API_KEY` is set, the hub can use the Firecrawl remote MCP instead.

**`mcp-docparser`** (capability: `doc_parse`)
| Tool | Input | Output |
|---|---|---|
| `parse_document` | `file_url, mime_type, filename` | `{text, tables[], pages, meta}` |

| Type | Library |
|---|---|
| PDF | `pymupdf`, with OCR fallback for scanned pages |
| DOCX | `python-docx` |
| XLSX/CSV | `openpyxl`/`pandas` → markdown tables |
| Images | Tesseract via `pytesseract`, with OpenAI vision fallback when OCR text is too short |
| Video/audio | `ffmpeg` → audio → OpenAI transcription (`OPENAI_TRANSCRIBE_MODEL`) |

Files are passed by **URL**, not by path: the backend exposes `GET /api/files/{id}?token=<signed, 10-min>`. This works inside Docker and also when the MCP runs remotely on FastMCP Cloud, as long as the backend is publicly reachable or tunnelled.

**`mcp-signals`** (capabilities: `web_search`, `news_search`, `social_search`, `job_search`, `enrich`)
| Tool | Input | Output (normalised `Hit`) |
|---|---|---|
| `search_web` | `query, since_days=30, limit=10` | `[{source, url, title, snippet, author?, published_at?}]` |
| `search_news` | same | same |
| `search_social` | `platform: x\|linkedin\|reddit\|facebook, query, since_days, limit` | same |
| `search_jobs` | `query, location?, since_days, limit` | same + `company` |
| `enrich_company` | `domain or name` | `{name, domain, industry, employees, hq, linkedin_url}` |
| `find_contacts` | `domain, titles[]` | `[{name, title, email?, phone?, linkedin_url?}]` |

- `PROVIDER_MODE=fixture` serves deterministic JSON fixtures (fictional companies and posts) and powers the demo. The fixture search does keyword/BM25 matching over the fixture corpus, so queries generated by the LLM still find relevant hits.
- `PROVIDER_MODE=live` routes to real providers whose keys are present:
  - Tavily or Exa for web and news.
  - X API v2 recent search for X.
  - Reddit API for Reddit.
  - LinkedIn and Facebook have no open search API, so they go through `site:linkedin.com/posts …` style queries on the search provider.
  - Jobs use `site:greenhouse.io OR site:lever.co OR site:linkedin.com/jobs` queries.
  - Enrichment uses Hunter or Apollo if keys are set.
- The tool contract is identical in both modes, so the pipelines don't change.

### 4.2 MCP registry (`mcp_servers.yaml`)

```yaml
servers:
  webscraper:
    url: ${MCP_WEBSCRAPER_URL}          # http://mcp-webscraper:9001/mcp
    auth_token_env: MCP_SHARED_TOKEN
    capabilities: [scrape]
  docparser:
    url: ${MCP_DOCPARSER_URL}
    auth_token_env: MCP_SHARED_TOKEN
    capabilities: [doc_parse]
  signals:
    url: ${MCP_SIGNALS_URL}
    auth_token_env: MCP_SHARED_TOKEN
    capabilities: [web_search, news_search, social_search, job_search, enrich]
  # Optional third-party remote MCPs — enabled only if their key env is set.
  # Verify exact URLs in each provider's docs.
  tavily:
    url: https://mcp.tavily.com/mcp/?tavilyApiKey=${TAVILY_API_KEY}
    enabled_if_env: TAVILY_API_KEY
    capabilities: [web_search, news_search]
    tool_map: { web_search: tavily-search }   # map capability → tool name + arg adapter
```

Servers are also mirrored into a `mcp_servers` DB table, so an admin UI can list them and show health later. For the MVP the YAML file is the source of truth.

### 4.3 MCP client: FastMCP `Client` vs LangChain MCP adapters

**Recommendation: FastMCP `Client`.**
- The servers and client use the same library and version, which gives first-class streamable HTTP, bearer auth, timeouts and an in-memory transport for unit tests (`Client(server_instance)`).
- Our pipelines are mostly **orchestrated** (fixed steps with LLM calls inside), not open-ended agents, so LangGraph isn't needed.
- For the one agentic step (optional "deep research" on a lead), a ~60-line adapter converts `client.list_tools()` into OpenAI function schemas.
- Switch to `langchain-mcp-adapters` only if we later adopt LangGraph agents.

`services/mcp_hub.py` sketch:
```python
class MCPHub:
    """One FastMCP Client per server; route by capability; isolate failures."""
    async def call(self, capability: str, tool: str, args: dict, timeout=60) -> Any: ...
    async def fan_out(self, capability: str, tool: str, args_list: list[dict],
                      concurrency=5) -> list[Result]: ...   # asyncio.Semaphore
    async def health(self) -> dict[str, bool]: ...           # client.ping()

async with Client(url, auth=BearerAuth(token)) as c:
    res = await c.call_tool("crawl_site", {"url": site, "max_pages": 15})
    pages = res.data  # structured output
```
Every MCP call is logged to `mcp_call_logs` (server, tool, latency, ok/error, truncated I/O) for debugging and cost tracking.

### AI document schemas (Pydantic → OpenAI Structured Outputs)

```python
class CompanyProfile(BaseModel):
    name: str; one_liner: str; description: str
    industry: str; sub_industries: list[str]
    products: list[Product]          # name, description, category, key_features[]
    value_propositions: list[str]; differentiators: list[str]
    target_markets: list[str]; geographies: list[str]
    customer_examples: list[str]; competitors: list[str]
    pricing_model: str | None; company_size_hint: str | None
    source_citations: list[Citation] # source_id + quote, to support every claim

class ICP(BaseModel):
    summary: str
    firmographics: Firmographics     # industries[], employee_range, revenue_range, geos[], tech_stack[]
    personas: list[Persona]          # title, seniority, department, goals[], pains[]
    pain_points: list[str]; buying_triggers: list[str]
    keywords: list[str]; negative_keywords: list[str]; exclusions: list[str]
    disqualifiers: list[str]

class SignalDef(BaseModel):
    name: str
    type: Literal["hiring","funding","expansion","leadership_change","tech_adoption",
                  "pain_post","rfp_tender","competitor_mention","event_participation"]
    channels: list[Literal["web","news","x","linkedin","reddit","facebook","jobs"]]
    description: str; queries: list[str]   # 2-5 concrete search strings
    weight: float; lookback_days: int

class HitQualification(BaseModel):
    relevant: bool; reason: str
    prospect_org: str | None; prospect_domain: str | None
    contact_name: str | None; contact_title: str | None
    matched_signal_type: str; confidence: float
    icp_fit: Literal["strong","medium","weak","none"]
```

## 6. Pipelines (arq jobs)

```
POST /workspaces/{id}/company  ──▶ ingest ─▶ build_profile ─▶ generate_icp ─▶ generate_signals ─▶ run_signals
                                 (each step is also individually re-runnable via API)
```

1. **`ingest(company_id)`**
   - Website: `scrape.crawl_site` → one `source` row per page (kind=website).
   - Uploads: `doc_parse.parse_document` per file, run in parallel (concurrency 3).
   - Text is cleaned and capped (around 150k chars total). Pages are ranked by relevance keywords before truncation.
2. **`build_profile`**
   - Map step: summarise each source (cheap model).
   - Reduce step: produce a `CompanyProfile` with citations (main model).
   - Skipped if `profile_edited` is true, unless `force=true`.
3. **`generate_icp`**: profile → `ICP`, saved as a new version and set active.
4. **`generate_signals`**: ICP → 5–8 `SignalDef`s. The prompt includes the available channels from the MCP registry, so the LLM only proposes signals we can actually run.
5. **`run_signals(company_id)`**
   1. Each active signal × query × channel becomes an MCP call through `hub.fan_out`, routed by capability (`jobs→search_jobs`, `x/linkedin/reddit/facebook→search_social`, `news→search_news`, `web→search_web`).
   2. Hits are normalised and deduped by `url_hash` (Redis set plus the DB unique constraint).
   3. Hits are qualified with the LLM in batches of 10 against the ICP, producing `HitQualification`. Irrelevant hits are dropped but kept in `raw_hits`.
   4. Leads are upserted by `dedupe_key`, linked through `lead_signals`.
   5. New leads are enriched with `enrich_company` and with `find_contacts` filtered to the ICP persona titles.
   6. Leads are scored (§6.1).
   7. Run stats are recorded. A per-run budget (`MAX_MCP_CALLS_PER_RUN`, `MAX_LLM_CALLS_PER_RUN`) guards cost.
6. **`draft_message(lead_id, channel)`**: the LLM drafts an email or WhatsApp message from the profile, ICP persona and the lead's signal evidence.

Progress is exposed through `GET /companies/{id}/status` (step, %, last error). The frontend polls every 2s; SSE is a later improvement.

Scheduling: a "Run signals now" button, plus an optional arq cron (`SIGNAL_RUN_CRON`, e.g. every 6h) for active companies.

### 6.1 Scoring (simple and explainable)
```
fit_score    = weighted ICP match (industry 0.35, size 0.2, geo 0.2, persona title 0.25), 0–100
               strong/medium/weak from LLM used when firmographics are unknown
intent_score = max over lead_signals of (signal.weight × confidence × recency_decay) × 100
               recency_decay = exp(-days_since / 21)
               +10 bonus per additional distinct signal type (cap 100)
score        = round(0.5 × fit + 0.5 × intent)
```
The feed shows the score breakdown on hover so users trust it.

## 9. Two Demo End-to-End Flows

Both demo companies are **fictional**, served from the local `demo-sites` container, and use `mcp-signals` in `PROVIDER_MODE=fixture`. This keeps the demo deterministic, means it needs only `OPENAI_API_KEY`, and avoids scraping real sites or people. A real company (for example Nokia at `https://www.nokia.com`) can be added through the UI at any time; it uses the live webscraper, and finds live leads once `PROVIDER_MODE=live` and search keys are set.

### Flow A: **NordWave Networks** (private 5G and industrial connectivity, Nokia-like)
- **Website:** `http://demo-sites:8080/nordwave/` with pages home, products (NW-Edge private 5G core, NW-Radio small cells, NW-Ops analytics), industries (ports, manufacturing, mining, utilities), customers, about.
- **Uploads:** `nordwave_brochure.pdf`, `nordwave_pricing.xlsx`, `nordwave_architecture.png` (OCR), `nordwave_webinar.mp3` (60-second transcript).
- **Expected ICP:** manufacturers, ports, mines and utilities in the EU and North America with 1,000+ employees. Personas: VP Operations, Head of OT, CIO, Plant Director. Pains: unreliable Wi-Fi on the shop floor, AGV/robot connectivity, Industry 4.0 rollout.
- **Expected signals:**
  - Hiring OT/Industry 4.0 network engineers (jobs)
  - New plant or terminal expansion (news)
  - Shop-floor Wi-Fi pain posts (reddit, x)
  - New CIO/CDO appointment (linkedin)
  - Automation capex or funding (news)
  - Private spectrum license news (news)

## 10. Docker & Local Run

**One command:**

- **If one physical container is required:** add an optional `Dockerfile.allinone` (supervisord running Postgres, Redis, uvicorn, arq, nginx and the three MCP servers) started with `docker run --name test-selloq --env-file .env -p 5173:5173 -p 8000:8000 selloq-allinone`. ## 13. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| LinkedIn/Facebook have no open search API, and scraping them breaches their ToS | Use public search indexes (`site:` queries through Tavily/Exa) or licensed data providers. Never automate logged-in scraping. |
| LLM cost/latency on large sites | Page cap and relevance ranking, a cheap model for map/qualification, per-run budgets, caching of MCP results in Redis (24h) |
| LLM hallucinated leads | A lead must come from a real `raw_hit` URL, and the LLM may only extract from the snippet. Evidence is always shown. |
| Personal data (GDPR/CCPA) | Store only business contact data, keep a source URL for each lead, add a delete-lead/forget function, add an unsubscribe footer to emails |
| Flaky remote MCPs | Per-server timeouts, retries with backoff, failure isolation in the hub, partial run results |
| Long-running jobs | arq with job timeouts, resumable step-level statuses, idempotent upserts |

## 14. How to Make It Better (post-MVP)

**Intelligence quality**
1. **pgvector embeddings** for the profile, ICP and leads. Semantic ICP-fit scoring and lookalike search ("find more like this qualified lead").
2. **Feedback loop:** Qualify/Disqualify clicks and reply outcomes re-weight signals and tune the qualification prompt per workspace, through few-shot examples taken from the user's own decisions.
3. **Multi-ICP & segments:** several ICPs per company (e.g. "Ports" vs "Mining"), each with its own signals and messaging.
4. **Account → contact graph:** roll multiple signals up to an account-level intent timeline, and add buying-committee mapping.
5. **Competitor intelligence:** track competitors' customers' complaints, reviews (G2/Capterra) and churn signals.
6. **Agentic deep-research** on a lead (LangGraph or an OpenAI tool loop over MCP tools): it builds a one-page account brief before outreach.

**Sources & MCPs**

7. More MCPs: G2 reviews, Crunchbase/PitchBook funding, government tenders (TED, SAM.gov), BuiltWith/Wappalyzer tech stack, GitHub activity, podcasts/YouTube transcripts, company filings.
8. A UI-managed **MCP marketplace**: add an MCP URL, auto-discover its tools, map them to capabilities, store per-workspace credentials encrypted (Fernet/KMS).
9. Playwright-based scraping for JS sites, plus a sitemap-first crawl strategy.

**Actions & workflow**

10. Real channels: WhatsApp Business Cloud API, Twilio voice with call recording and AI summaries, Gmail/Outlook OAuth sending with reply tracking.
11. Sequences: multi-step cadences with AI-personalised steps and auto-pause on reply.
12. CRM sync (HubSpot, Salesforce, Pipedrive) and Slack/Teams alerts for high-score signals.

**Platform**

13. SSE/WebSockets for live pipeline progress and real-time feed updates.
14. Teams and RBAC, audit logs, SSO, per-workspace usage metering and billing.
15. Observability: OpenTelemetry traces across API → worker → MCP → LLM, with Langfuse for prompt/cost tracking and Sentry.
16. Object storage (S3/MinIO) instead of the local volume; Temporal or Prefect if pipelines grow complex.
17. Evals: a golden dataset of hits labelled relevant/irrelevant, run in CI to catch prompt regressions; an LLM record/replay mode so CI runs without an API key.
18. Upgrade path to FastMCP 3.x when stable for the project, and use OAuth for remote MCP auth instead of shared tokens.

**Ideas from Explee (explee.com), a close comparable**

19. **Competitor-driven ICP:** crawl the competitors named in the profile and their public customer logos and case studies, then use them to sharpen the ICP and seed lookalike searches.
20. **Fit score per persona:** score each ICP persona (not only each lead) so users can see which buyer roles to prioritise.
21. **Campaigns with a preview gate:** group selected leads into a campaign and show the full lead list and drafted messages for approval before anything is sent.
22. **AI reply handling:** classify inbound replies (interested, objection, out of office, unsubscribe), draft responses, and book meetings through Calendly, Cal.com or HubSpot.
23. **Steer the agent in plain language:** a chat panel ("focus on ports in Northern Europe, skip companies under 500 people") that edits the ICP and signals for the user.
24. **Deliverability included:** pre-warmed sending domains and per-campaign cost-per-lead tracking.
25. **CSV import:** upload your own account list, and SelloQ validates, enriches and monitors signals on those accounts.
26. **Positioning:** Explee is driven by a contact database; SelloQ is driven by signals (live intent evidence). Lead with the "why now" evidence, and add a contact database such as Apollo or PDL only for enrichment.
